### Shipping

**Você é dono do que aterrissa. Verifique cada PR de forma independente, aterrisse só a execução verificada a partir da raiz, depois tire as mãos da pilha.**

1. **Resolva o forge, depois verifique cada PR de forma independente antes de aterrissar.** GitHub CLI (`gh`) é o padrão. Se `command -v origin` funcionar e o Origin conseguir resolver o repositório, use `origin pr` para toda operação de PR. Caso contrário, fique no `gh` e registre o fallback. Nunca exija Graphite (`gt`). Um verificador por PR, cada um um agente na nuvem do Cursor, roda a mudança do jeito que um usuário rodaria com a skill de controle correspondente (como `control-ui` ou `control-cli` do `cursor-team-kit`), pai contra head, e posta `PASS`, `PASS+NOTES` ou `FAIL` naquele PR. Só conta um veredito de um agente que não escreveu o código, porque um autor checa o que pretendia construir. CI verde e revisão aprovada de bot não são vereditos, porque nenhum dos dois roda a mudança como um usuário rodaria.
2. **Aterrisse só a execução verificada contígua com raiz embaixo.** Suba a partir do PR não mergeado mais baixo e pare no primeiro sem `PASS` ou `PASS+NOTES`. Os PRs abaixo dele são a execução, e o de cima é o teto. Um PR verificado acima de um não verificado espera, porque não consegue aterrissar sem o código abaixo dele. Um cujo branch nem contém nem precisa daquele código pode ir para o trunk e aterrissar sozinho. Ele precisa de um veredito novo primeiro, porque o antigo rodou com aquele código embaixo e o trunk não tem ele.
3. **Recheque que os vereditos ainda descrevem o código.** Um veredito cobre um patch, e um rebase em cadeia move todo PR acima dele para um SHA novo sem falhar em nenhuma checagem. Compare `git patch-id` no SHA do veredito com o head atual antes de confiar num veredito antigo. Quando os patches diferem só em testes, docs ou config de lint, o resultado de uma lane se mantém se o que ela rodou constrói o mesmo nos dois SHAs descontado o ruído. Ruído é uma diferença que também aparece entre dois builds do SHA do veredito, ou um SHA de commit embutido. Reporte cada tipo de ruído com os arquivos dele, para um leitor poder checar a decisão. A mudança em si ainda recebe checagens novas e uma revisão, porque o veredito antigo nunca a viu. Uma lane sem saída de build, como um dev server, não consegue mostrar isso, então rode de novo, e reverifique qualquer outra coisa que tenha derivado.
4. **Aterrisse de baixo para cima, um PR por vez.** Sempre merge o PR não mergeado mais baixo da execução, com `origin pr merge <pr>` ou `gh pr merge <pr> --squash`. No Origin o comando simples também merge todo PR abaixo do que você nomeou, e no GitHub um PR cuja base ainda é o branch do pai merge naquele branch, não no trunk. Leia o PR de volta para o resultado (`origin pr view <pr>` ou `gh pr view <pr> --json state,mergedAt,baseRefName`), porque um comando de merge pode reportar sucesso quando uma fila de merge só enfileirou o PR, e um auto-merge pedido não é merge. Um PR aterrissado aparece merged, com o trunk como base, não o branch do pai. Arme `--auto` (merge-when-ready do Origin ou auto-merge do GitHub) só num PR cujo veredito cobre o head atual dele, porque ele aterrissa qualquer head que esteja pronto. Depois que um merge aterrissa, retarget o PR cuja base era o branch mergeado para o trunk (`origin pr edit <pr> --base <trunk>` ou `gh pr edit <pr> --base <trunk>`), mova o patch dele para o resultado do merge, e faça push com `--force-with-lease`. O veredito cobre o patch, não os commits, então a regra de patch-id do passo 3 decide se o veredito sobrevive. Faça merge dele quando as checagens passarem e o veredito sobreviver.
5. **Deixe a pilha em paz enquanto ela aterrissa.** O movimento do próximo PR no passo 4 é a única mudança em branch ou base, porque um merge aterrissa o que o branch e a base dele tiverem naquele momento, com ou sem veredito. No GitHub, acompanhe a execução com `scripts/watch-pr/watch-pr --queued-stack` sob `/loop` até ele reportar `COMPLETE` no teto. Passe os números de PR da execução, de baixo para cima, em `--stack-prs`, e passe a mesma lista toda vez que reiniciar o watcher. No Origin, releia o PR atual com `origin pr view <pr> --checks` toda vez que `origin pr checks <pr> --watch` retornar, até o teto aparecer merged. Uma base que se move para o trunk quando o pai merge é esperada, não dano para consertar. Se um merge trava, descubra por quê antes de mudar qualquer coisa.
6. **Pare no teto.** Estender a execução exige vereditos novos, então é uma passada nova pelo passo 1.

**Resposta:** a execução verificada e o teto dela, o veredito de cada PR e quem o produziu, o que aterrissou e como você confirmou, e o que a próxima lacuna precisa.
